# **Architectural Specification and Product Requirement Document for a Polymarket Copy-Trading Infrastructure**

The emergence of decentralized prediction markets has fundamentally altered the landscape of information aggregation and speculative trading. At the forefront of this movement is Polymarket, a protocol that leverages the Polygon blockchain and the Gnosis Conditional Token Framework (CTF) to create a non-custodial, high-performance environment for wagering on real-world outcomes.1 The maturity of the Polymarket ecosystem, characterized by the introduction of the Central Limit Order Book (CLOB) and the Gamma API, provides the necessary primitives for the development of sophisticated automated trading tools.3 This report outlines the architectural requirements and product specifications for a professional-grade copy-trading system designed to monitor and replicate the activities of high-performance market participants in real-time.

## **The Evolution of Prediction Market Infrastructure**

The technical feasibility of a copy-trading engine on Polymarket is predicated on the transition from traditional Automated Market Maker (AMM) models to a hybrid-decentralized Central Limit Order Book.4 The CLOB architecture allows for off-chain matching and ordering while maintaining on-chain settlement via signed order messages, ensuring that users retain custody of their funds throughout the trading lifecycle.4 For a copy-trader to function effectively, it must navigate the complexities of the Gnosis CTF, which tokenizes outcomes as distinct ERC-1155 assets.2 These assets, known as positionIds, are derived through a rigorous cryptographic process involving conditionIds, collectionIds, and the underlying collateral token, typically USDC on the Polygon network.2

The derivation of these identifiers is a critical architectural concern. A conditionId is generated by calling the getConditionId function, which incorporates the address of the UMA oracle adapter, a bytes32 questionId, and an outcome slot count.2 Subsequently, collectionIds are derived using the getCollectionId function, which combines a parentCollectionId (usually null in the Polymarket context) with the conditionId and an indexSet representing the outcome slots.2 The final positionId is the result of the getPositionId function, linking the collateral token to the specific collectionId.2 A copy-trading engine must be capable of programmatically recreating these derivations to ensure it is monitoring the correct on-chain assets and avoiding malicious or spoofed tokens.

| Component | Function | Inputs |
| :---- | :---- | :---- |
| ConditionId | getConditionId | Oracle Address, QuestionId, OutcomeSlotCount |
| CollectionId | getCollectionId | ParentCollectionId, ConditionId, IndexSet |
| PositionId | getPositionId | CollateralToken Address, CollectionId |

## **User Interface and Target Address Management**

The primary entry point for the proposed system is a robust address management interface. The system must allow a user to specify a target Polymarket address, which then serves as the nexus for all monitoring and replication activities. This address is the proxy wallet address, which is automatically deployed for users upon their first login to the platform.8 The interface must provide a seamless lookup mechanism using the Gamma API’s profile and search endpoints to verify the validity of the target address and retrieve associated metadata, such as the user's pseudonym, bio, and historical performance metrics.3

The verification process is essential for maintaining a clean and maintainable codebase. Upon inputting a 0x-prefixed hexadecimal string, the system initiates a query to the GET /profiles or GET /public-search endpoints.3 This not only confirms that the address belongs to a registered Polymarket participant but also allows the system to populate a target dashboard with real-time data from the Data-API, including the total value of the user's positions and their current rankings on the global leaderboard.12 This architectural choice ensures that the user is making informed decisions based on the most current indexed data rather than stale blockchain history.

| Endpoint | Parameter | Description |
| :---- | :---- | :---- |
| GET /public-search | q | Searches for events, tags, and profiles matching the query. |
| GET /profiles | address | Retrieves metadata for a specific user wallet. |
| GET /value | user | Returns the total USDC value of a user's active positions. |
| GET /holders | market | Lists the top holders for a specific market outcome. |

The address input functionality must also incorporate safety checks to prevent the tracking of blacklisted or high-risk addresses. While the Polymarket exchange is non-custodial, the operator monitors for abuse related to balance and allowance manipulation.7 Integrating these checks at the UI level prevents the copy-trader from attempting to follow targets who may be subject to platform-level restrictions.

## **Real-Time Monitoring and Data Acquisition**

The technical core of the copy-trading infrastructure is the monitoring service, which must observe the target address with minimal latency. Polymarket provides two primary avenues for data acquisition: the Real-Time Data Socket (RTDS) and the Data-API.3 The RTDS is a WebSocket-based streaming service that delivers updates on various topics, including market activity and order matching.3 Although the activity subscription is currently noted as not being fully supported for all public users, it represents the ideal low-latency path for trade detection.3

When a trade is executed by the target, the RTDS emits an orders\_matched event within the activity topic.3 The payload for this event is exhaustive, containing the asset ID, the conditionId, the price at which the trade occurred, and the size of the execution.3 For a copy-trader, this real-time stream is the trigger for the rule engine. However, to ensure reliability and maintainability, a redundant system using the Data-API’s GET /activity endpoint is required.13 This endpoint returns on-chain activity for a user, including not only trades but also fundamental operations like splitting collateral into outcome tokens, merging tokens back into USDC, and redeeming winning positions.13

The choice between WebSocket and REST polling involves a trade-off between latency and consistency. While the RTDS provides immediate notification, the Data-API ensures that all on-chain state changes are captured, even those that might not trigger a matching event in the off-chain CLOB operator.3 A well-architected system will utilize the RTDS as the primary trigger and the Data-API as a secondary reconciliation layer to ensure no trades are missed due to socket disconnections or transient network issues.

| Event Type | Source | Significance |
| :---- | :---- | :---- |
| orders\_matched | RTDS (WebSocket) | Instant notification of a trade execution on the CLOB. |
| TRADE | Data-API (REST) | Confirmed trade record on the indexed data layer. |
| SPLIT | Data-API (REST) | Target is converting USDC into YES/NO token pairs. |
| MERGE | Data-API (REST) | Target is consolidating token pairs back into USDC. |
| REDEEM | Data-API (REST) | Target is claiming collateral from a resolved market. |

## **Advanced Sizing Logic and Rule Engine**

The differentiator of a professional copy-trading platform is the sophistication of its sizing rules. The user’s request for "various sizing rules" necessitates a rule engine that can calculate order parameters based on both the target's actions and the copier's financial status. This engine must handle floating-point arithmetic with extreme precision to avoid violating the CLOB's minimum tick size and size requirements.17

### **Proportional Percentage Sizing**

The most straightforward rule is the fixed percentage copy. In this mode, the system calculates the copier's trade size as a direct fraction of the target's execution. If the target purchases $10,000$ shares of a "YES" token and the copier has set a $5\\%$ rule, the system attempts to execute a purchase of $500$ shares.

The mathematical formulation for this is:

$$CopySize \= TargetTradeSize \\times Percentage\_{User}$$  
However, this calculation must be followed by a validation step against the CLOB's minSize parameter. If the resulting $CopySize$ is below the threshold, the trade must be discarded or rounded up to the minimum allowable size, depending on user preferences.17

### **Portfolio Scaling and Capital Efficiency**

A more advanced rule is proportional portfolio scaling, which ensures that the risk exposure of the copier matches the target relative to their respective total net worth on the platform. This requires the system to fetch the total value of both portfolios using the GET /value endpoint.13

The required trade size $S\_c$ for the copier is derived as follows:

$$S\_c \= \\frac{V\_c}{V\_t} \\times S\_t$$

Where:

* $S\_c$: Copier Trade Size  
* $S\_t$: Target Trade Size  
* $V\_c$: Total Value of Copier's Positions 14  
* $V\_t$: Total Value of Target's Positions 14

This scaling logic is essential for users following "whales" whose trade sizes might exceed the copier's entire balance. By using the GET /value endpoint, the system maintains an accurate denominator for these calculations, accounting for both USDC balances and the current market value of open positions.13

### **Fixed Notional Allocation**

For users who prefer a more conservative approach, the system must support fixed notional sizing. In this scenario, every detected trade by the target results in a trade of a fixed USDC amount for the copier, regardless of the target's size.

$$CopySize \= \\frac{FixedNotional\_{USDC}}{CurrentMarketPrice}$$  
This rule requires real-time price data from the CLOB’s /price or /midprice endpoints to ensure the share count calculation is accurate.19 Because Polymarket's CLOB is price-sensitive, the rule engine must also factor in the current bid-ask spread to avoid excessive slippage during the copy process.20

## **Authentication and Security Architecture**

Security is the cornerstone of any automated trading system. Polymarket utilizes a tiered authentication model consisting of L1 (Private Key) and L2 (API Key) levels.8 A professional copy-trader must implement these tiers in a way that prioritizes security while allowing for automated execution.

L1 authentication involves using the user's Polygon private key to sign messages.8 This is used to prove ownership and to create or derive L2 API credentials.8 The L2 credentials—consisting of an apiKey, secret, and passphrase—are then used to authenticate all subsequent requests to the CLOB API.8 These requests are signed using HMAC-SHA256, which provides a secure way to verify the integrity and authenticity of the API calls without exposing the private key.8

For the developer, the implementation of HMAC signatures is a critical path. The signature is constructed by concatenating the timestamp, method, and request path, then signing it with the base64-decoded secret.8 The resulting digest is then converted back to a URL-safe base64 string for inclusion in the headers.8

| Header Name | Required | Description |
| :---- | :---- | :---- |
| POLY\_ADDRESS | Yes | The user's Polygon signer address. |
| POLY\_SIGNATURE | Yes | HMAC signature for the specific request. |
| POLY\_TIMESTAMP | Yes | Current UNIX timestamp for replay protection. |
| POLY\_API\_KEY | Yes | User's unique L2 API key. |
| POLY\_PASSPHRASE | Yes | User's unique L2 passphrase. |

8

A key architectural recommendation is the use of the Polymarket Builder Program’s Relayer Client.21 This infrastructure allows the copy-trader to execute gasless transactions for its users.21 By utilizing Gnosis Safe-based proxy wallets, the platform can deploy wallets and perform Conditional Token Framework operations—such as token approvals and position splitting—without the user needing to hold MATIC or pay gas fees directly.21 This not only simplifies the user experience but also allows for atomic batch transactions where multiple operations can be executed in a single on-chain call.21

## **Execution Strategy and Order Management**

Placing the trade is the final and most complex step in the copy-trading workflow. All orders on the Polymarket CLOB are fundamentally limit orders, though they can be made marketable by adjusting the price relative to the current book.7 The system must support various order types to accommodate different market conditions and user preferences.

The primary order types supported by the CLOB are Good-Til-Cancelled (GTC), Good-Til-Date (GTD), Fill-Or-Kill (FOK), and Fill-And-Kill (FAK).17 For a copy-trader, FOK and FAK orders are particularly valuable. An FOK order ensures that the entire trade is executed immediately or not at all, preventing partial fills that could lead to an unbalanced portfolio.17 An FAK order, conversely, fills as much as possible at the current price and cancels the remainder, which is useful in highly volatile or illiquid markets.17

| Order Type | Abbreviation | Behavior |
| :---- | :---- | :---- |
| Good-Til-Cancelled | GTC | Order remains active until filled or manually cancelled. |
| Good-Til-Date | GTD | Order remains active until a specified Unix timestamp. |
| Fill-Or-Kill | FOK | Must be executed immediately in full; otherwise, it is killed. |
| Fill-And-Kill | FAK | Fills as much as possible immediately; cancels the rest. |

17

The execution engine must also strictly adhere to the tick size precision hierarchy. Failure to round prices and sizes to the correct decimal places will result in the INVALID\_ORDER\_MIN\_TICK\_SIZE error.17 According to the py-clob-client rounding configuration, the number of decimal places for price and size is intrinsically linked to the market's specific tick size.18

| Tick Size | Price Decimals | Size Decimals | Amount Decimals |
| :---- | :---- | :---- | :---- |
| 0.1 | 1 | 2 | 3 |
| 0.01 | 2 | 2 | 4 |
| 0.001 | 3 | 2 | 5 |
| 0.0001 | 4 | 2 | 6 |

18

For architectural reliability, the execution engine should utilize the createAndPostOrder method provided by the TypeScript or Python clients.23 This method abstracts the complex EIP-712 signing process and ensures that the order is properly structured for the on-chain binary limit order protocol.7 Furthermore, for copy-trading to be profitable, the engine must account for taker fees, which are calculated based on the baseRate and the specific market price.4

## **Negative Risk Markets and Strategic Adaptations**

A significant challenge in the Polymarket ecosystem is the presence of "Negative Risk" (NegRisk) events. These are multi-outcome markets where only one option can resolve as true, such as a presidential election with multiple candidates.24 Polymarket employs a custom NegRiskAdapter to increase capital efficiency in these scenarios.25

The architectural implication for a copy-trader is that a target may not merely be buying or selling shares but performing a "convert" action. In a NegRisk event, a user holding a NO share in one market can convert it into one YES share in all other markets within that event.25 This is mathematically equivalent and significantly more capital-efficient than selling the NO shares and buying the other YES shares separately.24

A robust copy-trading system must detect these conversion events via the Data-API’s activity stream.13 If the target performs a conversion, the copy-trader should replicate the same conversion using the NegRiskAdapter’s functions rather than attempting to replicate the end-state through individual CLOB trades. This ensures that the copier benefits from the same capital efficiencies and avoids the double-slippage associated with multiple market trades.24

Furthermore, the system must handle "Augmented Negative Risk," where placeholder outcomes are used to keep the outcome universe complete while new candidates are being identified.25 The PRD must specify that trading and copying should generally be restricted to named outcomes, as placeholder outcomes (e.g., "Person A" or "Person B") may have their definitions clarified later, potentially invalidating a previous trade logic.25

## **Scalability and Rate Limiting**

As a professional software architect, one must consider the operational constraints of the Polymarket API. The system is subject to both general and endpoint-specific rate limits that can impact the performance of an automated copy-trader.5 The general CLOB rate limit is $9,000$ requests per $10$ seconds, while high-frequency endpoints like order placement are more restricted.19

| Endpoint Category | Limit | Note |
| :---- | :---- | :---- |
| General Rate Limiting | 15,000 / 10s | Throttle on all requests. |
| CLOB POST /order | 3,500 / 10s | Burst limit for order placement. |
| CLOB POST /order | 36,000 / 10 min | Sustained limit for order placement. |
| CLOB Market Data | 1,500 / 10s | Limit for fetching book or price data. |
| Data-API Trades | 500 / 10s | Limit for retrieving historical trades. |

19

To mitigate these limits, the architecture should implement a distributed worker model with a centralized rate-limiting queue. By distributing the load across multiple API keys (if applicable) or by batching orders, the system can maintain high performance even during periods of extreme market volatility.17 Additionally, the system should leverage the higher tiers of the Builder Program. Moving from the "Unverified" tier ($100$ transactions/day) to the "Verified" tier ($1,500$ transactions/day) or the "Partner" tier (unlimited) is a critical requirement for scaling the platform to support a large number of users.26

## **Operational Maintenance and Error Handling**

A clean and maintainable codebase requires exhaustive error handling and observability. The copy-trader must be designed to gracefully handle various failure modes, such as insufficient balances, allowance issues, and order rejections.17

The system should implement a detailed logging and alerting framework that categorizes errors based on their severity. For instance, an INVALID\_ORDER\_NOT\_ENOUGH\_BALANCE error indicates that the copier's wallet needs funding, while an EXECUTION\_ERROR might suggest a transient issue with the CLOB matching engine that requires a retry.17 The system should also monitor for "Order Delayed" statuses, which occur when a marketable order is subject to a matching delay due to market conditions.17

| Error Code | Success Flag | Description | Recommendation |
| :---- | :---- | :---- | :---- |
| INVALID\_ORDER\_MIN\_TICK\_SIZE | Yes | Price breaks minimum tick size rules. | Verify rounding logic. |
| INVALID\_ORDER\_MIN\_SIZE | Yes | Size lower than the minimum threshold. | Adjust sizing rule min-limit. |
| INVALID\_ORDER\_NOT\_ENOUGH\_BALANCE | Yes | Insufficient funder balance/allowance. | Trigger alert for wallet funding. |
| ORDER\_DELAYED | No | Match delayed due to market conditions. | Implement exponential backoff retry. |
| MARKET\_NOT\_READY | No | System not accepting orders for this market. | Queue order for later execution. |

17

Beyond technical errors, the system must also account for market-level events such as resolution and redemption. Polymarket leverages UMA’s Optimistic Oracle for market resolution, a process that involves price requests, proposal bonds, and liveness periods.16 Once a market is resolved, the outcome tokens can be redeemed for USDC.28 A maintainable copy-trader will automate the redemption process, ensuring that user funds are converted back into collateral tokens as soon as the payout vector is reported on-chain.16

## **Economic Model and Builder Program Integration**

The final component of the PRD is the integration with the Polymarket Builder Program. This program provides not only the technical relayer for gasless transactions but also a mechanism for order attribution and fee sharing.21 By attaching custom builder authentication headers to every order, the copy-trading platform can get credited for the volume it generates.21

Order attribution allows the platform to compete on the Builder Leaderboard for grants and weekly rewards based on volume.22 More importantly, it enables access to the RevShare Protocol, allowing the platform to charge a custom fee on top of Polymarket’s base fee.22 This fee can be integrated into the rule engine, automatically adjusting the copier’s trade size to account for both the platform fee and the protocol fee, ensuring a transparent and sustainable business model.4

The builder credentials, consisting of a key, secret, and passphrase, must be managed with the same level of security as the users' API keys.21 Remote signing is the recommended approach for builders, where the credentials remain on a secure server while providing HMAC signatures to the client applications for relayer and CLOB access.21

## **Conclusion and Strategic Outlook**

The development of a copy-trading infrastructure for Polymarket is a multi-disciplinary challenge that requires a deep understanding of blockchain protocols, real-time data streaming, and automated execution strategies. By following the architectural guidelines outlined in this PRD—leveraging the Gnosis CTF for asset derivation, the RTDS for low-latency monitoring, and the Builder Relayer for gasless execution—a professional software architect can deliver a robust and maintainable system.

The convergence of prediction markets and automated trading represents a significant opportunity for market efficiency. As Polymarket continues to expand its market offerings and refine its technical stack, the role of automated tools in providing liquidity and price discovery will only grow. The proposed copy-trading engine is not merely a utility for individual users but a critical piece of infrastructure that bridges the gap between expert market analysts and the broader trading community. Through rigorous attention to detail in sizing logic, security, and protocol integration, this system will set a new standard for automated participation in the prediction market economy.
